# sapling-store

一个针对可变（mutable）数据修改的外部 store 库。

## 背景与问题

在 JavaScript 环境下，使用可变更新（直接修改对象/数组）可以显著减少短期对象分配，从而降低 GC 压力并提升性能。

但这样会带来与 React 等框架集成的兼容问题：

> - React 的 `useSyncExternalStore`（或类似的 external store + selector 模式）通常依赖 snapshot 变化来触发组件重新渲染。
> - 如果外部 store 直接复用内部对象引用，selector 可能继续拿到同一个引用，导致更新无法稳定传递到组件层。

## 当前方案

当前实现没有采用复杂的 selector 依赖路径追踪，而是走了一个更直接的 proxy notify 方案：写入发生时由 proxy 捕获变更，并通过通知机制把更新广播给订阅方。

这个方案保留了可变更新的低分配优势，同时实现足够轻量，适合性能敏感场景。

它的明显缺陷是：如果 selector 返回的是对象引用，而这部分引用本身没有发生变化，那么即使内部字段已经被可变修改，外层订阅也可能不会收到足够明确的更新信号。

## 设计理念（概要）

- 以 proxy 作为写入入口，直接拦截对象和数组的变更。
- 变更发生后只做通知，不强制把整棵对象树重新拷贝成不可变结构。
- React 侧通过订阅机制配合 `useSyncExternalStore` 读取最新值，把底层的可变更新接到组件渲染链路里。
- 在高频更新场景中，优先减少 GC 和临时对象分配，而不是追求完整的不可变快照。

## 基准观察

- 在约 100 万次计算规模的场景里，proxy notify 版本相较 zustand，计算时间大约少 100ms。
- 主要收益来自 GC 压力下降。
- 代价是会额外多占用约 2MB 内存；在高性能场景里，这部分内存和随之而来的 GC 开销会变成可见成本。

## 主要特性

- 支持可变风格的高性能更新（低 GC）。
- 基于 proxy 的变更通知机制。
- 适合对吞吐和延迟更敏感的场景。

## 简单示例

（下面示例基于库导出的约定 API，实际命名请参照 `src` 中的导出）

```ts
import { createUseStore } from 'sapling-store';

const useStore = createUseStore({ a: { b: { c: 0 } } });

function MyComponent() {
  const c = useStore((state) => state.a.b.c);
  return <div>{c}</div>;
}

useStore.proxy.a.b.c += 1;
```

在这个模型中，写入会通过 proxy 的通知链路传递出去，React 组件会在订阅更新后重新读取 selector 的结果。

## 注意与限制

- 这个版本更强调“通知”和“低分配”，不是完整的不可变数据层。
- 当 selector 返回对象或数组这类引用值时，需要特别注意引用稳定带来的更新不可见问题。
- 如果 selector 返回的是对象引用而不是原始值，需要特别注意引用复用带来的更新可见性问题。
- 在大量高频写入场景下，GC 收益通常更明显，但内存占用也会比更激进的不可变方案高一些。

## 贡献与扩展方向

- 继续补充更完整的 React 集成测试。
- 增强对对象引用返回值的更新感知，评估是否需要更细粒度的通知或额外的派生机制。
- 针对不同更新模式做更细的性能和内存对比。
- 评估是否需要更细粒度的通知与缓存策略。
